Roundest Cache performance pass

Local measurements from September 11, 2026. Baseline is commit c3d4d82, integrated is the current working tree. Both ran as production builds against a local KV fixture on the same machine. None of this is a production number.

What changed

The vote interaction and the results page were the slow parts. This pass fixed those two, then trimmed asset and bundle weight.

  • Votes advance on the client. The server prepares six pairs and ships them with the page. A click swaps in the next pair right away and posts the vote in the background. The queue refills four at a time when it runs low, and a failed vote offers a retry from a toast.
  • Results paginate at 50 entries. Page one shows the champion plus 49 challengers, later pages show 50, and the last page shows 25. Each response contains only the rows on screen.
  • Sprites load from jsDelivr instead of raw.githubusercontent.com. Each one carries width, height, decoding="async", and a fetch priority. The champion sprite loads eagerly at high priority. The rest stay lazy at low.
  • Sonner and next-themes left the first load. The Toaster mounts from a dynamic import, and the failure path imports sonner only when a vote fails. Dropping lucide-react and @vercel/functions paid for part of it.
  • Vote writes use after() from next/server instead of waitUntil from @vercel/functions. The write still happens after the response leaves. ignoreBuildErrors is gone from next.config.ts, and the build passes without it.

The click number comes from a local browser session where the baseline server action round trip was already only 17 ms. On a real network the baseline grows with RTT. The optimistic path does not.

What the numbers miss

The sprite change is partly a bet. Median delivery did not move, 17.3 ms for GitHub raw, 16.9 ms for jsDelivr, and the bytes are identical. What moved is cache lifetime, from max-age=300 to public, max-age=604800, s-maxage=43200, and the tail. Across two runs GitHub raw hit a 228 ms p95 and a 65 ms max while jsDelivr stayed under 32 ms. Repeat visits should feel the cache difference. First visits will not.

A burst test caught a bug I would have shipped. Twelve synchronous clicks batched their state updates, advanced the index past the queue, and unmounted the arena. The index now lives in a ref, so each click reads the real position. Eight clicks 40 ms apart produce eight distinct pairs and the buttons keep working. Ten votes produced 30 database commands on both builds, so after() writes what waitUntil wrote.

Method

  • Baseline c3d4d82 built in a separate worktree and served on port 4313. Integrated build served on port 4314.
  • A local KV fixture on port 4310 accepts MGET reads always and mutations only when a test turns them on.
  • Click latency runs from a MutationObserver that watches for the headline text to change, 10 alternating clicks per build, 300 ms apart, viewport 1280 by 800.
  • Page responses use three warmups and 15 samples, recording decoded bytes and gzip size.
  • Bundle numbers come from .next/diagnostics/route-bundle-stats.json because Next 16 no longer prints First Load JS.
  • Two image runs, 140 requests per host each, after a discarded warmup round.

Still open

  • The 15-second counter cache from the earlier pass is still a tradeoff. It cut 60 database commands across 30 warm results requests to zero, but local zero-delay responses were slightly slower than baseline. Keep it only if a real deployment shows the benefit it showed with a simulated 50 ms database delay.
  • Moving counters into one Redis hash would cut the cold read from two commands to one. Warm requests are already free, and the migration would risk existing votes, so the key layout stayed as it was.
